# Phase 4a — Customer bookings, tickets and account (design)

**Status:** decided 2026-10-13 under the owner's standing instruction to make every call. Each ruling in §2 says why it was made and what it costs if wrong. The owner asked to "pick up the customer side until the web team delivers".

**Branch:** `feat/phase-4a-customer-bookings`. It builds on the UI-A kit, the UI-B accounts work and the Phase 3 patterns.

**Requirements:** FR-2.7, FR-2.8, FR-2.10, FR-2.15 (in-app centre only), FR-2.23 (profile only), FR-1.9.

**Backend:** verified against web `origin/main` @ `30c7da90` and the production schema snapshot. See the customer-4a contract, summarised in `docs/BACKEND_STATUS.md` §7 and §9 by this phase.

**References:** `docs/design-references/2026-10-13-phase-4a-customer-bookings-mobbin.md`.

**Out of this phase:**

- Discover and listing detail (4b).
- Booking and payment, push, and claiming past guest bookings. All of these are blocked on web, and come in 4c.

## 1. Goal and success

A signed-in customer opens the app and, without any web work:

- sees their hotel, apartment and event bookings (upcoming first);
- opens a booking's details;
- shows a live event ticket at the door, or an offline code when the event allows it;
- shows the hotel check-in code at the front desk;
- reads and clears their notifications;
- edits their name, phone, state and address.

Tickets they have opened once still show with no connection.

Done when:

- On the Moto G06, against production, the QA customer's real bookings show correctly, the live code refreshes, and an admitted ticket shows "Admitted".
- The phone checklist's Phase 4a part passes.
- `tsc`, lint and jest pass.

## 5. Error handling

- Reads: transient errors never read as "you have no bookings". Show the saved wallet or `ErrorState` with **Try again**.
- Live code: §C7/C8. A 429 never blanks a valid token.
- Notification writes: §C13 zero-row guard; optimistic UI rolls back with a neutral banner.
- Profile save: transient → neutral banner and the form keeps its input; validation errors under the fields.

## 6. Accessibility and motion

- Targets are at least 44 pt.
- The QR has a label, and the code text is selectable (for reading out at the gate).
- The countdown ring is decorative; the text "refreshes every 30 s" carries the meaning.
- The live clock updates once a second without screen-reader announcements.
- Status chips always use word + colour.
- Reduce Motion: no pager animation and no ring sweep (static ring with the seconds as text).

## 7. Testing

- TDD for every pure unit:
  - Lagos boundaries for upcoming/past/today.
  - Each kind × status word.
  - Hidden-listing fallbacks.
  - Ticket ordering, seat and status.
  - Refresh delay and token validity under clock offset.
  - Every code-route outcome.
  - The check-in code rule.
  - The notification target map (bookingId hit or miss, each link path, unknown link).
  - Phone formats (`0803…`, `803…`, `+234…`, `234…`, invalid).
- API: column constants never include `email`, `password`, `role` or amounts beyond what's displayed; the profile update sends only the four fields; the zero-row retry.
- RNTL:
  - Bookings segments, empty state and the saved-wallet banner.
  - Ticket pager: poll only the visible ticket, 409 admitted, fallback by `require_dynamic_ticket`.
  - Check-in code gating.
  - Notifications: mark all read with undo, rollback on a zero-row write.
  - Account edit sheets.
- No production calls from tests.
- Device run with the QA customer's real bookings (an event ticket and a hotel stay). Book test items only through the real web flow, and refund or cancel them after.
