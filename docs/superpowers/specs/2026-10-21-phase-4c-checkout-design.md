## 1. Goal and success

A signed-in customer can:

- open a hotel room type, an apartment or an event;
- choose dates and guests, or tickets;
- review the server's price and pay with Paystack inside the app;
- end on "You're booked", with the booking in Bookings and event tickets live.

The phase must never:

- charge twice;
- show success before the server confirms payment;
- turn a transient failure into a refusal;
- leave a hold or booking the user abandoned.

The phase is done when, on the Moto G06 against production with the QA customer:

- one paid event booking completes end to end: tickets visible and the live code working;
- one free event registration completes;
- one hotel and one apartment booking complete, once #221 is live (until then the stay checkout is switched off, P2);
- killing the app on the Paystack page, then reopening it, resolves the payment without a second charge;
- backing out of review cancels the unpaid hold;
- every test booking is refunded or cancelled through the app or the web by the end;
- `tsc`, lint and jest pass, and the 4c phone checklist passes.

## 3. Pure logic (no React, unit-tested first)

- `domain/checkout/selection.ts`:
  - stay selection state and validation (dates in Lagos, nights, guests, min nights, max guests);
  - the event ticket map (P18) and answers (P17);
  - free-vs-paid (P19);
  - selection fingerprint, for idempotency key reuse.
- `domain/checkout/createRequest.ts`: builds the exact JSON body for hotel/apartment/event create from a selection. Snake_case, no money fields, positive integers only.
- `domain/checkout/createOutcome.ts`: maps create responses/errors to `{kind:'created', booking} | {kind:'refused', words, field?} | {kind:'unsure'} | {kind:'wait', seconds}`.
- `domain/checkout/paymentFlow.ts`: reducer for Review → Starting → InBrowser → Verifying → Polling → Done | Failed | StillChecking | HoldEnded. Polling schedule (P6), the P4 decision table from a check-status answer, and the P8 hold window.
- `domain/checkout/paymentStatus.ts`: maps status/verify/check-status bodies to `paid | failed | pending | unknown`.
- `offline/checkoutStore.ts`: P5 store (plainKv, per user, always-wiped).

## 4. API and hooks

- `api/checkoutApi.ts`: `createHotelBooking`, `createApartmentBooking`, `createEventBooking` (paid/free), `roomTypeAvailability`, `validatePromo`, `serviceCharge`, `initializePayment`, `checkPaymentStatus`, `verifyPayment`, `paymentStatus`, `findRecentEventBooking`. Every call goes through the one API client; zod schemas live in `schemas/checkout.ts`.
- Hooks: `useCheckoutSelection`, `useCreateBooking`, `usePayment` (drives `paymentFlow` with AppState/WebBrowser), `useResumePayments` (P5, mounted in the customer layout).

## 5. Screens and components

- **SelectScreen:**
  - Hotel: room summary card, dates row (opens `DatesSheet`), guests stepper, breakfast, airport, promo.
  - Apartment: dates, guests, airport.
  - Event: package rows with steppers, contact fields, questions, promo.
  - Sticky footer: estimate, then **Continue**.
- **PayScreen:**
  - Review: booking summary, your details, Price details (subtotal and discount from the server's `pricing`; service charge estimate from `/api/service-charges` labelled with its `label`; total), the hold line and **Pay ₦X**.
  - Checking, Failed, StillChecking and Done states.
- **New shared UI:** `DatesSheet` (month grid, range; RN-only, no new dependency), `Stepper` (44 pt targets, accessible "Adults, 2, increase/decrease").
- **Reused:** `TicketTypeRow` (with a stepper), `Banner`, `DetailRows`, `PriceTag`, `RateLimitWait`, `CharCounter`, `maskEmail`.
- **Listing integration:** `ListingFooter` / `RoomTypeCard` route to Select when the kind's switch is on, keeping the web hand-off otherwise. The "never promises booking in the app" note in 4b's footer is lifted only for switched-on kinds.
